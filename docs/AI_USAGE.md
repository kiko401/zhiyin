## 2 协作方法论

开发采用四条纪律约束 AI 协作，使 AI 产出可验收、可回溯、可纠正：

1. **契约先行**：编码开始前以三份定稿文档冻结全部契约（33 个接口、二十一表、决策表 D1–D11、降级矩阵 E1–E11、数据文件 Schema）。AI 只照契约填空，实现与契约不一致时一律修实现、不修契约——从机制上消除"AI 生成与需求漂移"这一最大返工源。
2. **里程碑冒烟门**：每个开发里程碑（M1 账号会话 → M2 意图引擎 → M3 任务引擎 → M4 持续任务 → M5 前端）定义可执行冒烟判据，判据不通过不进入下一里程碑。仓库保持线性增量提交（20 余次），每通过一次冒烟即 commit，提交节奏即开发节奏，可经 `git log --oneline` 复核（例：`7d56b46` 项目脚手架 → `4cc2bf4` 任务化执行引擎 → `10d88a8` 上线地址写入）。
3. **数据先行**：词典 400 条、金标 60 题、点子配置、五家公司底稿全部在编码开始前生成并冻结（仓库 data/ 目录），引擎联调一律消费真实文件，禁止临场造数据。
4. **并行子任务**：检查类工作（数据资产审查、服务器状态审计、测试套件编写）交由并行智能体执行，主开发线不被阻塞；审查结论与主线程产出交叉验证。

## 4 AI 产出的独立审查

数据资产在编码前经过一轮独立审查（以审查代理对照扶摇 API 与机制契约逐条核验），发现并修正：

- **事实核验**：51 个股票代码与名称对应关系经扶摇标的检索接口逐一客观验证，50 项通过；1 项修正——韦尔股份已更名豪威集团（603501.SH），词典与口径同步更正
- **格式缺陷**：词典 CSV 117 行存在字段槽位缺失（生成时漏写空列），全部补齐
- **分档校准**：72 条词条置信度不符合 PRD 2.2 分档规则（L1 须 ≥0.95、L2 上限 0.95），全部按规则重定档
- **口径对齐**：金标期望与词典现行释义存在 8 处漂移（如"断板"），以词典口径为准对齐金标

## 6 AI 生成代码的联调修正（工程层）

| # | 问题 | 根因 | 修正 | 验证 |
| --- | --- | --- | --- | --- |
| 1 | 注册接口 500（连接池 ping 崩溃） | SQLAlchemy pool_pre_ping 与 aiomysql 异步适配器不兼容 | 改用 pool_recycle=1800 | 注册/登录/登出全流程回归通过 |
| 2 | 任务创建 1406 报错（Data too long for column 'blueprint'） | 字段 VARCHAR(32) 不足以容纳六工具蓝图序列 | 扩至 VARCHAR(128)，两库对齐 | 任务创建与蓝图记录正常 |
| 3 | 四段式回答生成为空（E1 证据卡降级） | flash 模型推理消耗超出 max_tokens=1200 上限 | 生成调用提至 4000 | 四段式 DELIVERED，4 条引用齐全 |
| 4 | 会话状态更新报错（Row 不可变） | Core select 与 ORM select 混用 | 统一 ORM select | 会话状态机流转正常 |
| 5 | 卡片不落库（历史回放缺系统卡片） | 异步辅助函数被同步调用，协程未执行 | 改为同步函数 | 历史回放含完整卡片序列 |

## 7 运维事故处置记录

部署当日服务器出现 infra 中间件四容器全部无法启动（Exited 两个月前）。AI 辅助完成根因链路定位：Docker 启用 containerd 镜像存储后，其快照层数据丢失而元数据残留，属宿主机异常重启后的存储损坏，无法原地恢复。处置方案：确认 MySQL/Redis 数据位于命名卷（与镜像层无关，数据完好）→ 移除损坏容器与镜像 → 依赖服务器预配置镜像源重拉 → 按原编排配置以 docker run 重建并固化维护脚本 run-infra.sh（同机 docker-compose v1 与新版 Docker 存在已知兼容性断裂）。全程约 12 分钟恢复，期间验证了"高风险项前置到准备阶段暴露"的排期决策有效性。

## 9 小结

本轮协作中，AI 承担了契约内实现、数据起草与检查类工作的主体产能；候选人的价值集中在三处：机制契约的设计与冻结（决定"做什么与不做什么"）、AI 输出的验收标准制定（冒烟判据先行，问题当场消化）、以及对 AI 错误的系统性纠正（每次修正均落为规则或测试，而非一次性修补）。产品内全部关键数字来自数据面并带引用四要素，模型输出经确定性校验器把关——AI 的能力边界由产品机制显式管理，这也是本产品"模型负责语义、规则负责边界、引擎负责过程"立场的实践印证。
